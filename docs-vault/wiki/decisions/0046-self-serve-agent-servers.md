# ADR-0046: Self-serve agent servers with per-account caps

Status: proposed. Needs the owner's approval (decisions and the questions at the end). Issue #517.

## Context
- ADR-0045 Amendment 1 (owner, 2026-10-20, option B): a player on a rented host must be able to get a server without
  the operator before the mod's first public release. This design, its build, gate B (#186), #514, #515, #516 and #311
  are all gates on that release.
- ADR-0020 already sketched the flow ("Add server" creates the server and the owner membership in one transaction and
  shows a single-use code; public ids are 20 random base32 characters, `0020-multi-user-data-model.md` lines 30-41), and
  ADR-0030 phase 2 says the backend never connects to a player's host. This ADR makes that concrete and adds the caps.
- Paths are under `backend/src/modules/` unless they start with a top-level directory.

## Decision

### 1. Creating a server (no operator, no connection test)
1. `POST /api/servers/agent` (new; `agent` joins `RESERVED_SERVER_IDS`, `packages/shared/src/serverManagement.ts:12`).
   Any signed-in, active account. Body `{ displayName }` only. Mounted with the other collection routes, before the
   servers router.
2. Self-serve servers are born `agent`: no host, no tokens, no connection test, no outbound connection (ADR-0030
   phase 2). The mod or agent connects out with a code.
3. The public id is generated by the backend (20 random base32 characters, ADR-0020) with a plain INSERT. Never the
   upsert: a player must not be able to pick an id or revive a deleted server's id and whatever it left behind (R3).
4. A new column `servers.servers.created_via` (`operator` default, `self_serve`). Caps, the managed list and the
   pending-server sweep key on it. Existing rows become `operator` by the default.
5. One transaction, under the existing management advisory lock (`TAKE_SERVER_MANAGEMENT_LOCK`): re-check the caps
   (section 2), insert the server (`connection_kind = 'agent'`, `created_via = 'self_serve'`), add the caller as owner,
   write `server.created` (ids only, `detail: { via: "self_serve" }`). After the commit the runtime gains an agent entry
   (the same builder enrolment uses, `backend/src/server.ts:173,322-336`).
6. #311's rule in the database too: a deferred constraint trigger on `servers.servers` INSERT refuses a commit that
   leaves a `self_serve` server with no owner row. (Operator-created rows stay exempt: the startup seed covers them,
   `servers/loadDatabaseServers.ts:75-86`.)
7. The player then gets a code from the existing agent settings (`POST /api/servers/:id/agent/enrollment-codes`,
   owner or admin) and pastes it into the mod's config (`FactoryGame/Configs/SatisDashAgent.cfg`, `enrollmentCode`;
   mod spec line 58). Enrolment itself is unchanged: on an `agent` server the switch is a no-op kind write.
8. The owner may rename and remove a self-serve server they own: the existing `renameAgent` and `remove` entries gain
   a contract flag `selfServeOwner: true` (the precedent is `memberSelfService`, `serverAuthorization.test.ts:286`).
   The generated authorization suite then tests: owner of a self-serve server 200; owner of an operator server 403;
   admin and viewer 403; non-member 404. Remove reuses `softDeleteServer`.
9. Membership middleware is unchanged, so every self-serve server gets the same non-member 404 as any other.

### 2. Per-account and total caps

All `self_serve` only; the operator's account is exempt (`canManage`). Numbers are recommendations (owner question 2).

| # | Cap | Number | Why | Enforced |
|---|---|---|---|---|
| C1 | Self-serve servers an account owns | **2** | One dedicated server is the normal case; a second covers a test world. Each server multiplies #514's and #515's budgets | In the create transaction; `server_limit_reached` (existing code) |
| C2 | Live self-serve servers in total | **25** | One backend instance, 20 GB of RDS with no autogrow. Re-derived when #515 states its per-server row bound: C2 = (free storage minus the 3 GiB alarm headroom) / per-server steady-state bytes, rounded down, halved for safety | Same; `server_limit_reached`, message says the service is full |
| C3 | Pending (never enrolled: no `agents.agent_credentials` row) servers per account | **1** | You enrol one before creating the next; empty servers can't be stockpiled | Same transaction; `server_limit_reached` naming the pending server |
| C4 | Pending server lifetime | **24 h** | A sweep soft-deletes a `self_serve` server with no credential row older than this, freeing C1/C2 slots | Automatic, in the existing sweeper pattern (`agents/services/commandSweeper.ts`) |
| C5 | Server creations per account | **5 / 24 h** | Stops create/delete churn around C1 (each leaves a soft-deleted row and audit rows) | In-memory `UserRateLimiter`, 429 |
| C6 | Open codes per server | **1** (today) | Structural: a new code deletes the old (`agentsService.ts:72`), so open codes per account <= C1 | Unchanged |
| C7 | Codes issued per account | **10 / min (today) and 20 / hour (new)** | A setup needs 1 to 3 (a typo, the 10-minute expiry). Bounds enrolment churn and its audit rows | Second `UserRateLimiter` in `agentsService` |
| C8 | New accounts, process-wide (open sign-up only) | **20 / hour** | Bounds multi-account farming of C1-C3 | Count of `identity.users.created_at` in the last hour, in the sign-up transaction; refused `signup_busy` |
| C9 | Members per server | n/a | No members API exists yet (ADR-0025 1b). When it lands: 20 members, 10 pending invites | That build |
| C10 | Alert destinations | today's | 1 Discord per server, 50 rules per server, 10 push devices per user (table above) | Unchanged |

**How they compose with #514 and #515.** An account's worst case is C1 x #514's per-credential budget (requests, bytes,
one long-poll) and C1 x #515's per-server quotas (history rows, alert subjects and events, fair outbox claim). The
service's worst case is (C2 + 8 local) x the same. So #514 and #515 must land first: C2 is computed from #515's number,
and C1 is only safe because each server's cost is bounded.

**Who raises a cap: the operator only, by configuration.** `SELF_SERVE_MAX_SERVERS_PER_ACCOUNT`,
`SELF_SERVE_MAX_SERVERS_TOTAL` and the others above are environment settings (the PC's `.env`; on AWS the task
definition / SSM), validated at startup with fail-fast bounds, the way `identity/googleConfig.ts` validates its own.
A restart applies a change. There is deliberately no API for caps. Lowering a cap never deletes existing servers; it
only refuses new creates. A per-account override is "not yet" (below).

### 3. Kill switches
- `SELF_SERVE_ENABLED` (default `false`): off means `POST /api/servers/agent` answers 403 `forbidden`; existing servers
  keep working.
- `SIGNUP_MODE` (`closed` default, `open`): closed is today's behaviour. Open creates the user, identity and session in
  one transaction on the first verified sign-in (ADR-0025 decision 3), within C8.
- Both stay off in production until every gate in section 7 is closed and the owner says go.

### 4. Enrolment limiter and code length (M2)
- Codes become 60 bits: `XXXX-XXXX-XXXX` (12 base32 characters), and the process-wide enrol limit goes from 120 to
  1,200 a minute. The per-network 10 a minute stays.
- Why: one open code per server, so at most C2 + 8 = 33 open codes. A year at the global cap: 40 bits at 1,200/min is
  6.3e8 x 33 / 2^40, about 0.019 (a 2% chance of one hijack a year, too high); 60 bits is about 1.8e-8. Today's 40 bits
  at 120/min with 8 codes is about 5e-4 (ADR-0045 M1). Lockout then needs about 120 distinct /64 networks held for as
  long as the attack lasts, instead of 12.
- Why now: the mod pins the format (spec lines 41-42). Before its first release it is a one-line change there; after,
  every installed mod would need an update. It is a contract change of its own (task 2), with a brief to the mod
  session.

### 5. Abuse response

| Who | Action | Where |
|---|---|---|
| Automatic | C1-C8 refuse; #514 refuses an over-budget credential (429) and counts refusals per server; #515 drops excess history rows and caps alert fan-out; C4 sweeps pending servers; `rds-free-storage-low` alarms | sections 2, #514, #515 |
| Operator | `disable-user` (#516) also revokes the agent credentials of the servers the account owns, in the same transaction (data kept; after re-enabling, the owner re-enrols) | #516, amended |
| Operator | `remove-server <public-id>`: full delete of any server (#516's "leaves nothing" list). Needed as a CLI because the HTTP remove 404s for a non-member, and the operator is not a member of self-serve servers (Context) | #516, amended |
| Operator | `list-servers`: every server with `created_via`, owner user id, enrolled, last seen, and history row counts, ids only | #516, amended |
| Operator | Turn off `SELF_SERVE_ENABLED` or `SIGNUP_MODE`; lower a cap; restart | section 3 |

No automatic disabling or deletion of enrolled servers or accounts: one false positive deletes an honest player's
history, and one operator can respond within hours. Reopens when #514's counters show more abuse than that.

### 6. What does not change
- **Operator-created servers:** nothing. They become `created_via = 'operator'`, are not counted by any cap, keep the
  connection test, `MAX_LOCAL_SERVERS` and the operator-only routes as they are. Operator servers switched to an agent
  stay `operator`.
- **The operator's powers:** all kept. They gain three CLI commands (section 5). The managed list
  (`GET /api/servers/managed`) shows `created_via = 'operator'` servers only, so it never offers rename or remove on a
  server whose scoped routes would 404 for the operator. The operator can't read a self-serve server's dashboard
  (not a member), which is intended.

### 9. Privacy
- **A self-serve owner sees** exactly what an owner sees today: their server's live data, history, alerts, its agent
  status and codes. Nobody else's server (non-member 404). Mod v1 sends player counts only (ADR-0045 Amendment 1).
- **The operator sees** (CLI, ids): every server's name, public id, owner user id, enrolment state, last seen and row
  counts, plus the database itself as data controller.
- **Privacy-page changes the build needs** (task 8; the owner writes or approves the copy, `frontend/public/privacy.html`):
  1. The Google-account row (line 44, "matching you to invitations") also covers creating an account on first sign-in.
  2. A new row: enrolment and agent data per server (hashed one-time codes, a hashed credential, the agent or mod
     version, last-seen time).
  3. What the mod sends (player counts, game-world data), next to the existing player-names row (lines 83-87).
  4. The operator may disable an account or delete a server for abuse, and what deleting your own server removes
     (everything in #516's list); pending servers are removed after 24 h.
  5. The account-deletion paragraph (lines 165-167) matches what #311 builds.
  The terms page's suspension line (`frontend/public/terms.html:72`) already covers disabling; check it names server
  deletion too.

## Consequences
- Strangers can get a server only once every gate is closed and both switches are on; until then the code ships dark.
- The mod's code format changes before its first release (task 2); the mod session needs a brief.
- Two limits (C5, C7) are in memory, like every limiter here; a second instance multiplies them (ADR-0045 "Revisit
  when").
- The operator stops being every server's owner; "the operator can do anything through the dashboard" no longer holds
  for self-serve servers. Abuse handling is CLI.

## Explicitly deferred
| Pattern | Not yet because | Trigger |
|---|---|---|
| Per-account cap overrides (admin CLI and a table) | No player has asked | The first legitimate request for more than C1 |
| Automatic quarantine of a noisy server or account | False positives cost honest data; volume is tiny | #514's counters show abuse faster than manual response |
| Invite-only sign-up (ADR-0025 1b invites) | Contradicts "without the operator" | The owner prefers it (question 1) |
| Members API and its caps (C9) | Not needed for one-owner servers | ADR-0025 1b is scheduled |
| A shared limiter store (Redis) | One instance | A second backend instance |
| Tenant sharding, read replicas | 25 servers on one t4g.micro | Measured contention after #515, never before |

## Revisit when
- #515 states its per-server bound (recompute C2).
- C2 is reached, or pending servers exceed half of it (M3's residual).
- A second backend instance (in-memory limits).
- The members API (1b) is built (C9).

## Questions for the owner
1. **Sign-up:** fully open to any verified Google account behind `SIGNUP_MODE` and C8 (recommended), or invite-only?
2. **Cap numbers:** C1 = 2, C2 = 25 (recomputed after #515), C3 = 1, C4 = 24 h, C5 = 5 a day, C7 = 20 an hour, C8 = 20
   an hour (recommended as listed)?
3. **Code length:** 60-bit codes now, which changes the mod's spec before release (recommended)?
4. **Disable:** should `disable-user` also revoke the account's servers' agent credentials (recommended), or only stop
   sign-in?
5. **New accounts' display name:** a neutral generated one such as "Player-XXXX" (recommended; nobody shares a server
   with a stranger yet), or the email's local part, as the privacy page currently allows?
6. **Terms acceptance:** a "by signing in you agree to the Terms" line on the sign-in page, or an explicit acceptance
   recorded at account creation (an audit event with the terms version)? Recommended: the explicit one, since strangers
   now create accounts; this is a legal call.
