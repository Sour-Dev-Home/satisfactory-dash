- 2026-09-25 — ADR-0027 PR 4, the history API (contract and routes together, so the generated IDOR tests picked the new server-scoped routes up at once). Shared: `history.ts` (query and response schemas for power, items and transitions; the range picks the resolution), three `endpoints.history.*` entries (with a `query` schema; every query is optional, `range` defaults to 24h), fixtures `historyPower24h` (1-minute source), `historyItems7d` (hourly source) and `historyTransitions24h`, drift-tested by name prefix. Backend: `historyQueryRepository.ts` (constant SQL, bound parameters, `date_bin` with a bound interval from the Unix epoch so buckets are UTC-aligned, weighted averages, min of mins, max of maxes), `HistoryQueryService` (per server by public id) and `routes/history.ts`. Design (the architect's four changes): the source is chosen by the target bucket, not the range (1-minute rollups only below 1 hour, hourly rollups otherwise, so 30d reads 720 rows per series, not 43,200); power series never merge across game sessions (`{ session, circuit, points }`, newest data first); every read is a transaction with a bound `statement_timeout` of 5 s (a timeout or any database failure is a 503 `service_unavailable`, cause kept for the log, and "all items" is capped at 50 by highest average rate with `truncated`); each series stays at or under 600 points by construction. Members only through the existing guard; a bare GET works; a bad query is a 400 naming the parameter, never the value; 503 without a database; the in-memory `/power/history` is untouched. Tests: the service with a fake pool, the routes, the generated IDOR tests (the test bundle gained a history stub), and a real-Postgres test (CI only) for the re-bucketing math, the source selection, session separation, the item cap and the transitions. `runbooks/history.md` documents reading history. Demo handlers and any UI are the frontend's follow-up.
