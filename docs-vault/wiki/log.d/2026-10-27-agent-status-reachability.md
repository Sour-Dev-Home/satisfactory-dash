- 2026-10-27 — The agent status shows whether the agent can reach the game (#740 follow-up). Backend: every accepted snapshot (an unreachable one too) hands `gameReachable`, `lastGameReadAt` and `modVersion` to a per-process `GameConnectionStore` (agents module), which keeps the latest values in memory and writes them to three new nullable columns on `agents.agent_credentials` (migration `1792195200000_agent_game_connection`, expand-only) in the agent version's pattern: only a change, with a `lastGameReadAt` that merely moved forward written at most every 30 s, one write at a time per server, retried after a failure. `lastGameReadAt` only moves forward (in memory and with `GREATEST` in SQL), and one more than 60 s ahead of the backend's clock is ignored. A snapshot without the fields (an older agent) clears the reachability and version. `GET /api/servers/:serverId/agent` returns them for an enrolled agent: the memory's values when it has heard from the agent since the start, else the database copy, and the later `lastGameReadAt` of the two. Frontend: Settings, Game PC agent gains a "Game" line: a check and "Reachable" (ok token) or a warning triangle and "Not reachable" (warn token), with "last read 9 s ago" (or "not read since the agent started"); while the agent is offline it says "Unknown while the agent is offline" and still gives the last read. The version line adds the sender's `modVersion` only when it differs from `agentVersion`. Demo agent, two MSW scenarios and e2e states (`agent-game-reachable-owner`, `agent-game-unreachable-owner`).
