- 2026-09-26 — ADR-0027 PR 6, alert delivery: the transactional outbox and the Discord sender, behind a kill switch. **`ALERT_DELIVERY=on|off`, default OFF** (`alerts/config.ts`; anything else, including "true" or "1", stops the backend at startup naming the variable; `on` also needs a database and `SERVER_SECRETS_KEY`; the startup log states the mode): while off the engine still records events but writes NO outbox rows and sends nothing, and switching it on later sends only transitions after that. Migration `1790726400000_alert_delivery` (a deploy needs `db:migrate` first): `alerts.destinations` (one per server and kind; the webhook sealed with `platform/secrets` AES-256-GCM, bound to the server by the context `alerts:<server uuid>:discord`, key id, last 4 characters readable, `enabled` plus a `disabled_reason`, a CHECK that a disabled one has a reason) and `alerts.outbox` (one row per event and destination, unique `(event_id, destination_id)`, status pending/sent/dead, attempts, `next_attempt_at` doubling as the lease, a stable error code only). `writeEvaluation` enqueues in the SAME transaction as the events when delivery is on. `AlertDeliveryWorker` (only when on; every 10 s) claims due rows of enabled destinations with `FOR UPDATE SKIP LOCKED` and a 2-minute lease (at-least-once), opens the webhook with the keyring, and records `sent`, a retry with exponential backoff (30 s doubling to 30 min, never sooner than a 429 `retry_after`), `dead` after 24 hours or a permanent refusal, or, on a 404 or 401 seen again on a row's second attempt (the first is retried a minute later, so one glitch cannot kill a working destination), disables the destination and gives up on its pending rows. Deleted servers are excluded from both the enqueue and the claim. Security: `discordWebhook.ts` allows only `https` to exactly `discord.com` or `discordapp.com` with Discord's webhook path (no userinfo, port, query, fragment, subdomain, IP, encoded characters or backslash), checked when saved AND again just before every send; `discordSender.ts` re-validates, sets `redirect: "manual"` and refuses any 3xx without reading `Location`, has a deadline, and reduces every failure to a code (a thrown error can quote the URL); logs and results never carry the URL or token. `alertMessage.ts` escapes game text (mentions, markdown, links, control and bidi characters), bounds the size and sets `allowed_mentions.parse` to empty; the unreachable alert says "Game server or FRM not responding" (it also fires when only FRM is down). `sendAlertTest` (for the rules API, PR 7) honours the switch: `delivery_off` with nothing sent. `npm run admin -- set-alert-webhook <server-id>` sets a webhook from stdin until the API exists. A soft delete also removes the destination and its outbox. The privacy page gains the Discord webhook and alert rows, the Discord processor line (which says Discord also sees our server's IP address as the sender), the 90-day/24-hour retention, "and send alerts" again, and the date. `runbooks/alerts.md` has the enabling steps. Tests: URL allowlist (44), sender (19), backoff, message escaping, delivery worker with a real keyring (redirects, 429 pause, 404 disable, expiry, unreadable and tampered secrets, no URL in any log), the kill switch and its atomicity, send-test, config, and a real-Postgres test (CI only) for the sealed storage and context binding, the atomic enqueue, claim concurrency, leases, disabling and cascades.
