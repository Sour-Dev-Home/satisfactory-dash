- 2026-10-16 — `db:init` works with a non-superuser `CREATEROLE CREATEDB` admin, as on RDS (#421, contract fix for #420, ADR-0025/0034). Since PostgreSQL 16 such an admin holds the roles it created with `ADMIN` but no `SET`/`INHERIT`, so `CREATE DATABASE ... OWNER satis_migrator` failed with `must be able to SET ROLE`, and RDS's `db_name` database already existed owned by the master. `backend/src/platform/db/admin.ts` now grants the admin `SET` (with `INHERIT FALSE`) on `satis_migrator` only when it lacks it (never for a superuser), revokes it in a `finally` (after `RESET ROLE`, reporting both errors if the revoke itself fails), hands an existing database with another owner to the migrator, and runs the database and `public` grants as the migrator via `SET ROLE` (`ALTER DEFAULT PRIVILEGES` no longer needs `FOR ROLE`). It also grants the admin `CONNECT` on the database: without it a non-owner admin could not connect once `PUBLIC` lost `CONNECT`, so a second run failed (found while testing; the issue's wording runs the grants under `SET ROLE`, which alone cannot re-run). New `nonSuperuserAdmin.db.test.ts` (its own Postgres 18 container, so the admin creates the satis roles itself and no other file re-provisions them concurrently) covers a new and an admin-created database (each provisioned twice), a failing step revoking the grant, a half-done RDS database, and an admin that already held `SET` keeping it. `runbooks/aws.md`: "Check the backup role" resolves its `[NEEDS VERIFICATION]` (the grant succeeded on RDS PostgreSQL 18, 2026-10-16) and explains both behaviours; Apply step 4 lists every first-apply target and how PowerShell quotes them; "Running an ops task" adds a PowerShell `run_ops`. `infra/aws/README.md` does not repeat step 4, so it is unchanged.
