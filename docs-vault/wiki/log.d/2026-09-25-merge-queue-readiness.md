- 2026-09-25 — ADR-0033 C, merge queue readiness (harmless before the ruleset flips, which the coordinator does after this merges; a merge group can't be run before then). `ci.yml` and `e2e.yml` gain `merge_group` (`checks_requested`); the log fragment step stays `pull_request` only. In e2e, a merge group always runs everything (its `changes` job has no base to diff, deliberately), pixels are always compared there, baselines are regenerated only for a manual `workflow_dispatch` with `update_snapshots` (never in a merge group), and a missing baseline directory FAILS in a merge group (it stays report-only elsewhere); a merge group's run is never cancelled by a newer one. New `.github/workflows/fresh-eyes-gate.yml` (on `merge_group`; permissions `statuses: write`, `pull-requests: read`, `contents: read` only; actions pinned by commit SHA; the script is checked out from the queue's BASE commit, not the merge group commit, so a queued PR can't change the code that vouches for it; no untrusted text in `run:`): `scripts/fresh-eyes-gate.mjs` parses the PR number from `merge_group.head_ref` with a strict regex (`gh-readonly-queue/main/pr-<N>-<sha>`, anything else fails closed), reads that PR head's combined status for `fresh-eyes/test-hunter`, and posts the same context on `merge_group.head_sha` (success with "carried from <sha7>" only if the PR head's latest such status is a success, otherwise failure "no fresh-eyes success on PR head"; any API failure is a failure). Unit tests (`scripts/fresh-eyes-gate.test.mjs`, 12) cover the parsing, the decision and the fail-closed paths with a fake `gh`; the e2e baseline step was also simulated for every event type. The real proof is the coordinator's first docs PR through the queue after the flip. The gate also refuses a PR that is not open and based on `main`, and reads the PR head's combined status with `per_page=100` and paging (a fresh-eyes finding: the default page of 30 could push the context off the first page). Security review (no exploitable finding; nothing runs before the queue is on) left three requirements for the flip, written in the workflow header: merge group size max AND min = 1 (the payload names only the last queued PR); protect the workflow file, the script and CODEOWNERS with a CODEOWNERS entry plus required Code Owner review (or a ruleset path restriction, or a required workflow pinned to main), because GitHub reads a merge group's workflow file from the merge group commit, so a PR that edits `fresh-eyes-gate.yml` controls what the gate posts; and note that the gate trusts whoever can post the `fresh-eyes/test-hunter` status, the same trust the ruleset already places in it.
