- 2026-10-20 — #348 task 2/3, the web push sender (ADR-0044). When an alert event is written with push enabled (`ALERT_DELIVERY=on`, VAPID configured, a secrets keyring), the same transaction queues one outbox row per subscription of every current, active member who opted in for that server. The existing `AlertDeliveryWorker` claims push rows from the same outbox with #515's per-server turns (a row's server is now its event's server, so push and Discord rows share one partition) and hands them to `pushDelivery.ts`, which rechecks the recipient just before sending (still a member, `identity.users.status = 'active'` per #516's review, still opted in) and drops the row otherwise (`recipient_*` codes, metric `satis.alerts.push.dropped`). The endpoint is re-checked against the allowlist at send; redirects are never followed; 10 s timeout. Encryption is RFC 8291 `aes128gcm` and VAPID RFC 8292 ES256 on `node:crypto` (no new dependency; RFC 8291's worked example is a unit test). The payload is the Discord message's words with game text cleaned as plain text, at most 3 KB. 404/410 deletes the subscription (audited `alerts.push.subscription_gone`), 429 and 5xx retry with the existing backoff, other 4xx drop the row. `POST /api/push/subscriptions/:id/test` now really sends a fixed test notification. No contract change; runbook `alerts.md` has a web push section. The service worker and UI stay 348-3.
