- 2026-09-26 — ADR-0027 PR 5, the alert engine (records events only; delivery is PR 6 behind `ALERT_DELIVERY`, the rules API PR 7). New module `backend/src/modules/alerts/` (edges alerts -> telemetry and alerts -> servers through their indexes; `architecture.test.ts` and `workspace.dsl` updated, 19 edges) and a new `alerts` schema (migration `1790640000000_alerts`: `rules`, `alert_state`, `alert_events`, `server_mutes`; `LATEST_MIGRATION` moves, so a deploy needs `db:migrate`). Telemetry gains an in-memory `ObservationBoard` per server (only with a database): the power poller publishes the status (paused, session), the circuits with the dashboard's own `classifyPowerCircuit` status and its poll failures, the factory poller publishes each machine's derived state, best output percent and recipe, and flags the FIRST snapshot after a pause. The pure state machine (`alertStateMachine.ts`: `ok -> pending -> firing`, fired / renotify / resolved, hysteresis helper, `resumeAfterSuppression`, unknown readings hold the last condition, time going backwards is clamped) has table-driven and seeded random-sequence property tests (no fire without `for`, no resolve without the clear duration, renotify spacing, and a state reloaded from JSON at any step gives the same transitions). `ServerAlertEvaluator` decides a tick from its inputs and only advances its in-memory state on `commit()`, after the storage succeeded: kinds `power_outage` (per circuit), `fuse_trip`, `server_unreachable` (3 failed polls and 2 minutes) and the grouped `stopped_machines` (per-machine timers in memory, group phase persisted under subject `group`, `updated` when new machines join a firing group at most every 10 minutes, a firing group adopts the stopped machines after a restart); suppression while paused, unreachable or muted; a stale reading is unknown. `AlertEvaluatorWorker` runs every 30 s (only with a database), seeds the presets idempotently for every server, skips a rule with unreadable params with a logged code, writes the changed states and the events in ONE transaction, and purges events older than 90 days (the alerts module runs this itself, since telemetry may not import alerts). Presets: `power_outage`, `stopped_machines` (below 5 percent for 5 minutes, clear 2 minutes) and `server_unreachable`; `fuse_trip` exists but is not seeded, because today an "outage" IS a tripped fuse and two alerts would say the same thing. A soft delete also deletes the server's rules, states, events and mute (same as history). Tests: the state machine, the evaluator scenarios, the worker over an in-memory fake of the tables (atomic write, restart, failed write, unreadable rule, mute, purge cadence, the loop), the board and both pollers' publishing, and a real-Postgres test (CI only) for seeding, the one-transaction write and its rollback, the round trip, the purge and the soft-delete cleanup. `runbooks/alerts.md` documents it (deploy order, kinds, suppression, restarts, the SQL to read the alert log during the shadow run). Architect's review change: a machine counts as stopped when it is `underfed` OR `backedUp` (output full, the most common real case) AND its best output percent is below 5 (a backedUp machine at a higher percent is intermittently full, not stopped); the group summary now says why per machine (`byReason`: "output full", "input short: <ingredient>", counted), which needs the observation to carry the classifier's `missingInput`.
