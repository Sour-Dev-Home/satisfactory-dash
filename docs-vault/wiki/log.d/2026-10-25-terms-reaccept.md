- 2026-10-25 — #568 (#530 decision 9): an existing account re-accepts a materially changed Terms version at its next Google sign-in. The sign-in service compares the account's recorded `terms_version` with `TERMS_VERSION`; when it is older, the callback refuses with a new code `terms_changed` (audited as `signin.refused`, with the user id) and starts no session, so nothing else is reachable until the person accepts. The sign-in page then shows "The Terms have changed": a short "what changed" list (`TERMS_CHANGES`, beside `TERMS_VERSION` in `frontend/src/auth/googleSignIn.ts`), a link to the Terms, an unticked box, "Continue with Google" (the same `?terms=` round trip as sign-up) and "Decline and stay signed out". Accepting writes the new version and time on the user row and a `terms_accepted` audit row (versions only). `/start` now keeps the ticked version whatever the sign-up mode (an unknown account is still refused `not_invited` while sign-up is closed), and the router's `signupOpen` option is gone. The C8 hourly count also requires `created_at` within the hour, so a re-acceptance never uses up the sign-up cap. Accounts that never accepted any version (invited, the operator) are not asked, and a disabled account is still a plain failure. No migration (the columns exist since #528), and `TERMS_VERSION` is unchanged. The privacy page says the record is replaced after a re-acceptance (dated 25 October 2026); the terms page is untouched, since its date is the terms version. New e2e state `login-terms-changed`.
