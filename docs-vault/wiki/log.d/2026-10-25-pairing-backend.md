- 2026-10-25 — ADR-0051 section 1 and ADR-0057 D6, the backend half of device-code pairing. New table `agents.pairings` (migration `1791936000000_agent_pairings.sql`, additive: only the SHA-256 of the 128-bit pairing secret, the 60-bit user code, the agent's session name and version, expiry, poll bookkeeping, approver id and server). Routes: `POST /agent/v1/pairings` (unauthenticated; 6 an hour per network, 600 an hour process-wide, the network hit refunded when the global refuses) and `/agent/v1/pairings/poll` (`pending | expired | slow_down | approved`; slow_down is tracked per row and grows the expected interval by 5 s up to 60; an unknown, spent or expired secret reads as `expired`; `approved` mints the credential with the SAME step as enrolment, `installAgentCredential`, in the transaction that spends the pairing, so one use); `POST /api/pairings/lookup` and `/approve` (signed in; 10 a minute and 20 an hour per account, operator exempt from the hourly one, plus 30 a minute per network, every try counts; an unknown, spent, expired or not-owned code or server is the one 404 `not_found`); `GET /api/compat` (served from `COMPAT_POLICY` in `agents/config.ts` for now, a table later). Approving a NEW server runs the self-serve create (caps C1 to C5, kill switch) with the approval inside its transaction (`SelfServeService.create`'s new `inTransaction` hook), so a refused cap or a lost race leaves no server; approving an existing one is owner-only. A `PairingSweeper` deletes rows an hour after they expire (so the session name and agent version live at most about 75 minutes), and `frontend/public/privacy.html` gains the matching retention row. New counter `satis.pairing.events` (`started | approved | expired`). Module edge: `agents` uses `servers`' `lockServerForPairing` and the self-serve create through the composition root; no new import edge.
