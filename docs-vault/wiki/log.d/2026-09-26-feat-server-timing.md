- 2026-09-26 — ADR-0032 step 1, the server-time split. Every request now has a timer (`platform/requestTiming.ts`, AsyncLocalStorage): the game-adapter's two clients report each call to the game server (vanilla API or FRM, success or failure) through a new optional `onUpstreamCall` on `SatisfactoryServerConfig`, wired in `server.ts`; a request's upstream time is the UNION of those intervals (two parallel 200 ms calls wait 200 ms, not 400) and app time is the rest. The response carries `Server-Timing: app;dur=..., upstream;dur=...` (always both), and `Timing-Allow-Origin` echoes an allowlisted frontend origin only (never `*`, and `Vary: Origin`). The request's log line gains `appMs`, `upstreamMs`, `vanillaMs`, `frmMs`, `upstreamCalls` and `route` (the matched pattern, e.g. `/api/servers/:serverId/status`, never the concrete URL). New `npm run latency-report` (`scripts/latency-report.mjs`, reads `$LOG_DIR` or `--dir`/`--file`, `--days`, `--json`): p50, p95 and p99 per route (total, app, upstream) and per game-server API, proven by a unit test on a committed fixture log (`scripts/fixtures/latency-sample.log`). Durations and route patterns only: nothing personal is logged. No API latency targets yet (ADR-0032: after a week of baseline).
